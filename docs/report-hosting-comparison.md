# 호스팅 운영 방식 비교 보고

**주제:** 카페24 리셀러 vs 스마일서브 iwinv 자체 호스팅  
**목적:** 웹에이전시 고객사 호스팅 인프라 방향 검토  
**현재:** 카페24 리셀러로 운영 중  
**검토안:** iwinv 가상 서버 + 웹호스팅 제어판(Plesk/aaPanel)

---

## 1. 요약 (Executive Summary)

| 구분 | 내용 |
|------|------|
| 공통점 | 고객에게 도메인·계정·용량 단위의 “호스팅 방”을 제공하는 사업 모델 |
| 핵심 차이 | **서버 소유·장애 책임·원가 구조**가 다름 |
| 카페24 리셀러 | 운영 부담↓, 안정·확장 용이, 마진·구성 자유도 제한 |
| iwinv 자체 | 구성·원가 통제↑, 기술·장애·백업 책임이 전부 내부로 이전 |
| 권고(일반) | 전면 전환보다 **병행·단계 이전** 검토. 특수·대용량 고객부터 자체 검토 |

---

## 2. 비교 대상 정의

### 2-1. 카페24 리셀러 (현행)

- 카페24 호스팅 상품을 도매로 받아 고객에게 재판매·관리
- 서버·네트워크·플랫폼 운영의 상당 부분을 카페24가 수행
- 에이전시는 계정 생성, 도메인 연결, 고객 응대, 과금에 집중

### 2-2. iwinv 자체 호스팅 (검토안)

- 스마일서브 클라우드(iwinv)에서 가상 서버를 직접 구매·운영
- 제어판으로 고객별 사이트(방)를 생성·관리
- OS·웹스택·백업·보안·장애 대응을 내부에서 수행

---

## 3. 구조적 차이

```
[카페24 리셀러]
에이전시 ──(계정 생성)──▶ 카페24 멀티서버 플랫폼
                              ├─ 서버1 (고객들)
                              ├─ 서버2 (고객들)
                              └─ ...

[iwinv 자체 — 초기]
에이전시 ──(제어판)──▶ iwinv 가상서버 1대
                              ├─ 고객A
                              ├─ 고객B
                              └─ ...

[iwinv 자체 — 규모 확대 시]
에이전시가 서버를 늘려 고객을 수동·반자동 분산
  (카페24와 “여러 대” 형태는 닮으나, 자동 배정·통합 플랫폼은 별도 구축 필요)
```

| 관점 | 카페24 리셀러 | iwinv 자체 |
|------|---------------|------------|
| 서버 소유 | 카페24 | 에이전시 |
| 고객 방 위치 | 카페24 서버 팜 | 우리가 구매한 VM |
| 방 분리 기술 | 공유 호스팅(계정·vhost 등) | 동일 계열 (제어판이 구현) |
| 멀티노드 | 플랫폼이 기본 제공 | 서버를 늘리면 유사 형태 가능. 자동 프로비저닝은 별도 |

> 서버를 여러 대 늘리면 **분산 형태**는 비슷해질 수 있으나, 카페24 수준의 **자동 배정·통합 관리 플랫폼**과는 동일하지 않음.

## 4. 항목별 비교표

| 항목 | 카페24 리셀러 | iwinv 자체 호스팅 |
|------|---------------|-------------------|
| 초기 구축 | 빠름, 기존 프로세스 유지 | 서버·패널·보안·백업 구축 필요 |
| 운영 난이도 | 낮음~중간 | 중간~높음 |
| 장애 1차 책임 | 플랫폼 비중이 큼 | **내부** |
| 보안·패치 | 플랫폼 + 계정 관리 | OS·패널·스택 **직접** |
| 백업 | 상품/정책 범위 | 외부 백업 **직접 구축 필수** |
| 구성 자유도 | 상품 스펙 내 | PHP·Apache·모듈 등 **높음** |
| 브랜드·네임서버 | 가능 (정책 범위) | 마스터 도메인·NS까지 자체화 용이 |
| 고정비 | 고객 없으면 서버비 거의 없음 | **서버 월정액** 발생 |
| 변동비 | 고객·상품 수에 비례 | 트래픽·디스크·서버 추가 |
| 마진 | 도매가 대비 판매 마진 | 원가 통제 시 규모에서 유리할 여지 |
| 확장 | 상품 추가가 단순 | 스펙업·서버 추가·이전 작업 |
| 고객 체감(방) | 계정별 독립에 가까움 | 도메인·용량·DB 분리. 서버·IP는 공유(기본) |

## 5. 장단점

### 5-1. 카페24 리셀러

**장점**
- 서버 운영·대규모 인프라 부담이 적음
- 장애·네트워크 이슈 대응에 플랫폼 지원을 기대하기 쉬움
- 고객 증가 시 상품 단위 확장이 비교적 단순
- 초기·인력 관점에서 진입·유지 비용이 낮음
- 현재 운영 중이라 전환 리스크 없음

**단점**
- 상품·기능·PHP/모듈 등 **제약**에 걸릴 수 있음
- 원가·마진 구조가 플랫폼 정책에 종속
- 특수 요구(구버전·커스텀 서버 설정)에 불리할 수 있음
- 인프라 단 통제권·가시성이 제한적

### 5-2. iwinv 자체 호스팅

**장점**
- OS·웹스택·용량·보안 정책을 **직접 설계**
- 장기·대량 고객 시 원가 구조 개선 여지
- 마스터 도메인·네임서버·제어판으로 **자체 브랜드 호스팅** 형태 가능
- 레거시·특수 환경(예: Apache + 특정 PHP) 맞춤에 유리

**단점**
- 장애·보안·백업·용량의 **최종 책임이 내부**
- 고객 0명이어도 서버 고정비 발생
- 인력·기술(리눅스·패널·보안) 필요
- 단일 VM 집중 시 장애 영향 범위가 큼 (서버 분산·백업으로 완화 필요)
- 카페24형 자동 멀티노드 운영을 그대로 대체하려면 추가 구축 필요

## 6. 비용 관점 (개념)

| 비용 | 카페24 리셀러 | iwinv 자체 |
|------|---------------|------------|
| 고정비 | 낮음 | 가상 서버(+스토리지) 월정액 |
| 변동비 | 계정·상품 수 | 트래픽 초과, 디스크, 서버 추가, (선택) Plesk |
| 숨은 비용 | 상대적으로 적음 | 장애 대응·관리 인건비·학습 비용 |
| 무료에 가까운 항목 | — | Let's Encrypt SSL, aaPanel(선택 시), 자체 NS(운영 비용은 별도) |

※ 구체 금액은 시점·스펙·계약에 따라 달라지므로, 의사결정 전 **고객 N명 기준 월 납부액 vs 서버 월정액** 시뮬레이션 권장.

## 7. 기술·격리에 대한 오해 정리

| 질문 | 답 |
|------|-----|
| 방마다 도메인이 다른가? | 예 |
| 방마다 용량·DB·SSL을 나눌 수 있는가? | 예 (제어판) |
| 방 = 완전 별도 서버인가? | **기본은 아님** (공유 호스팅 모델) |
| 서버를 늘리면 카페24와 같아지나? | **분산 형태만 유사**. 자동 배정·통합 플랫폼까지는 별개 |

## 8. 적용 시나리오 제안

| 시나리오 | 적합 방식 |
|----------|-----------|
| 안정·운영 최소화, 현행 유지 | **카페24 리셀러 유지** |
| 특수 스택·커스텀·특정 대형 고객 | **iwinv 자체 (일부)** |
| 장기적으로 호스팅 원가·브랜드 내재화 | **자체 비중 단계적 확대** |
| 리스크 분산 | **병행** (일반=리셀러, 특수=자체) |

### 단계적 접근 (권고안 예시)

1. **Phase A:** iwinv 1대 + 제어판 + 외부 백업 구축 (파일럿)
2. **Phase B:** 신규·이전 용이 고객 소수 입주, 운영·장애 절차 검증
3. **Phase C:** 손익·안정성 검토 후 확대 여부 결정
4. **Phase D:** 고객 증가 시 서버 추가·분산 (필요 시)

## 9. 자체 호스팅 전환 시 생길 수 있는 어려움

카페24 리셀러에서 iwinv 자체로 옮기거나 병행할 때 나타날 수 있는 이슈다.

| 영역 | 어려움 | 영향 |
|------|--------|------|
| **장애 대응** | 서버 다운·디스크 장애·네트워크 이슈를 내부에서 직접 진단·복구해야 함 | 복구 지연 시 다수 고객 사이트 동시 영향 |
| **보안** | SSH 노출, 패널·CMS 취약점, 계정 침해 대응이 온전히 내부 책임 | 한 서버 침해 시 같은 VM의 다른 방으로 확산 위험 |
| **백업·복구** | 외부 백업·복구 절차를 직접 만들고, “백업은 있는데 복구가 안 되는” 상태 방지 필요 | 실수·랜섬·디스크 장애 시 데이터 손실 |
| **사이트 이전** | CentOS7 → Ubuntu, PHP 7.3 → 7.4/8.x 등 환경 차이로 깨지는 사이트 발생 가능 | 이전 직후 오류·일정 지연, 고객 불만 |
| **노하우·인력** | 리눅스·제어판·방화벽·DB 운영 지식이 꾸준히 필요 | 담당자 부재 시 대응 공백 |
| **단일 서버 집중** | 초기 1대에 고객을 모으면 장애·점검 영향 범위가 큼 | 트래픽 폭주 고객 1곳이 전체 성능 저하 |
| **비용 착시** | 고객이 적을 때는 리셀러보다 **고정비(서버)** 가 더 비쌀 수 있음 | 파일럿 구간 손익 악화 |
| **운영 복잡도** | 서버 추가 시 어느 서버에 넣을지·이전·모니터링을 수동·반자동으로 관리 | 카페24형 자동 배정이 없어 실수 증가 |
| **고객 응대** | “호스팅이 안 돼요”의 원인이 코드·DNS·서버·패널 중 무엇인지 구분해 설명해야 함 | 응대 시간·기술 부담 증가 |
| **이중 운영** | 리셀러와 자체를 병행하면 계정·청구·모니터링 창구가 둘로 갈라짐 | 관리 누락·혼선 가능 |

**요약:** 자체 호스팅의 어려움은 기술 구축 자체보다, **장애·보안·이전·인력·고정비**를 플랫폼 대신 내부가 짊어지는 데 있다.

---

## 10. 결론

- **카페24 리셀러**는 운영 효율·안정 측면에서 현행에 유리하다.
- **iwinv 자체 호스팅**은 통제권·맞춤·장기 원가 측면에서 의미가 있으나, **인프라 사업자 수준의 책임**이 따른다.
- 보고 시점 권고는 **전면 대체보다 파일럿·병행 후 확대**이다.
