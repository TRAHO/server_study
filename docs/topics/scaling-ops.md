## 무엇이 달라지는가

| 상황 | 특성 |
|------|------|
| **단일 서버 집중** | 초기 1대에 고객을 모으면 장애·점검·트래픽 폭주의 영향 범위가 큼 |
| **서버 추가** | 어느 서버에 넣을지·이사·모니터링을 내부에서 설계 (카페24형 자동 배정 없음) |
| **리셀러와 병행** | 계정·청구·모니터링 창구가 둘로 갈라져 누락·혼선 가능 |
| **고객 응대** | “호스팅이 안 돼요”가 코드·DNS·서버·패널 중 무엇인지 구분해 설명해야 함 |
| **비용** | 리셀러는 고객 수에 비례해 납부, 자체는 서버 단위 원가 — 규모가 클수록 구조 비교가 필요 → [costs.md](../costs.md) |

## 대응 방향

1. **초기:** VM 1대 + 여유 스펙으로 시작, 리소스 모니터링
2. **분산:** 고객·트래픽이 늘면 서버를 나누고, 신규는 여유 서버에 배정
3. **분리:** CPU·트래픽을 많이 먹는 고객은 단독·고스펙으로 분리
4. **병행 시:** 어느 고객이 리셀러/자체인지 목록·청구 기준을 문서화
5. **응대:** 1차 확인 순서 고정 (DNS → 서버 생존 → 패널/사이트 → 앱 로그)
6. **인력:** 담당 부재 시를 대비한 접속 정보·런북 공유 → [incident-response.md](./incident-response.md)
